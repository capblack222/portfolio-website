AgriSense Agent

2025 · capstone, Google × Kaggle AI Agents Intensive

A retrieval-augmented advisory agent for smallholder farmers that attributes every recommendation to the sources it was retrieved from, rather than to model weights.

the problem

A farmer asking whether to irrigate today needs an answer tied to this crop, this growth stage and this week's weather. A language model will answer that question fluently whether or not it knows anything — and a confident wrong answer about fertiliser timing can cost a season's yield.

So the interesting constraint was not generating advice. It was making every piece of advice traceable to a source, and being able to tell whether a change to retrieval made the answers better or merely different.

decisions

  • Grounded every answer in retrieved agronomy text. Irrigation thresholds, heat limits and pest names come from a local vector index at query time and are injected into the prompt, so the model is summarising retrieved evidence rather than recalling it.
  • Fixed a 30-pair evaluation set before tuning retrieval. Without it, judging a retrieval change means reading a few answers and forming an impression. With it, two versions are comparable.
  • Ran the weather fetch and the retrieval concurrently. They are independent, and doing them in sequence spent the sum of two latencies to gather context the model needs in one go.
  • Kept a deterministic rule engine behind the model. Crop and stage-aware thresholds still produce an answer when the LLM is unavailable, so the failure mode is a plainer recommendation rather than no recommendation.

architecture

how it was built

  • Knowledge base chunked at roughly 600 characters with overlap, embedded with Bedrock Titan V2 into 1024-dimension vectors and stored in a Chroma index built once by an ingest script.
  • JWT authentication with bcrypt hashing, per-user and per-IP rate limiting, CORS locked to the frontend origin, and request validation at the schema layer.
  • Four test modules covering the rule engine, the weather client, the chunker and the retrieval evaluation harness.

what I would change

The Chroma index lives on local disk, which is the thing that stops this being genuinely deployable: it ties the service to one machine and makes the retrieval tier non-replaceable. Moving it behind a managed vector store is the next real change, and the evaluation set exists precisely so I could tell whether that migration made retrieval worse.

The evaluation set is also still small at 30 pairs, and I wrote them myself — which means it measures consistency against my own reading of the agronomy guides, not against an expert's.
