AWS 3-Tier Infrastructure Platform

2026

A three-tier AWS architecture defined entirely as code, with one module set serving three environments.

  • 0

the problem

The fastest way to get dev, staging and production stood up is to copy the configuration three times. It is also the fastest way to get three environments that have quietly diverged, so that a change tested in staging behaves differently in production for reasons nobody can reconstruct.

The goal was one definition, three instantiations, and no copy-paste between them.

decisions

  • Split modules by lifecycle, not by service. Networking, security, compute, storage and monitoring change at different rates and for different reasons. Grouping by what changes together keeps a routine compute change from touching the VPC.
  • Used conditional resource counts instead of per-environment copies. One codebase parameterised by environment, so dev can run a smaller instance count without being a different configuration. Drift between environments becomes impossible rather than merely discouraged.
  • Put the database in private subnets behind a NAT gateway. The data tier has no inbound route from the internet at all. Outbound access for patching goes through NAT, so the isolation is structural rather than a security-group rule somebody could widen.

architecture

what I would change

State management is the gap. For this to be safe with more than one person applying it, the backend needs remote state with locking — otherwise two concurrent applies can interleave and leave the recorded state describing infrastructure that does not exist.

I would also add a plan-only CI step on pull requests. Reviewing a Terraform diff as code is much harder than reviewing the plan it produces.
