the problem

A worker pool sized for peak capacity is idle most of the time and expensive all of the time. Sized for the average, it falls behind the moment traffic spikes and never catches up.

The usual autoscaler answer is CPU, and for queue-driven work CPU is the wrong signal entirely. A worker blocked waiting on a message looks idle to the scheduler, so the pool scales down exactly when the backlog is growing. The thing that actually describes the load is the number of messages waiting.

decisions

  • Scaled on queue depth, not CPU. KEDA reads the SQS queue length and sets the replica count from it. The signal matches the work: ten thousand waiting messages means scale out, regardless of what the processor is doing.
  • Kept SQS between SNS and the workers. SNS fans out, but it does not hold anything. A queue in between means a slow or restarting consumer causes a backlog rather than dropped messages.
  • Validated scale-in, not just scale-out. Scaling up under load is the easy half and the half everyone demos. The 100-message test watched the pool return to one pod afterwards, because an autoscaler that never scales down is just an expensive fixed pool.
  • Scoped IAM inline policies to the queue. The workers can read and delete from one queue and do nothing else.

architecture

what I would change

There is no dead-letter queue. A message that fails repeatedly currently cycles rather than being parked for inspection, and that is the first thing I would add before putting this anywhere real.

The 15-second polling interval was not derived from anything — it is a reasonable default. Tuning it is a trade between how fast the pool reacts and how often KEDA calls the SQS API, and I would want a cost figure on both sides before choosing a number deliberately.
