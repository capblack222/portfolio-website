the problem

An agent scans a ticket and needs an answer immediately: is this a winner, and has it already been claimed. Two things make that harder than a database lookup. The read is hot — the same draw gets verified thousands of times — and the answer must never be stale, because a cached winner shown twice is a paid claim shown twice.

So the system wants aggressive caching everywhere except the one case where caching is dangerous. Most of the design follows from holding both of those at once.

decisions

  • Excluded WINNER outcomes from the cache. Everything else reads through Redis; winners always read through to Postgres. A stale hit on a losing ticket costs nothing. A stale hit on a winner could show one agent a claim another has already paid.
  • Kept a shared RDS instance over database-per-service. The textbook answer is to split. I did not, because the SQS payload already carries enough context for the claims service to operate without reading the verification tier — so the split would have bought isolation I was already getting, at the cost of a second database to run.
  • Put claim processing behind SQS with a dead-letter queue. Three retries, then the message parks in the DLQ for 14 days. Verification stays available when the claims service does not, which is the failure mode that actually matters at a counter.

architecture

how it was measured

  • Custom CloudWatch metrics — CacheHit, CacheMiss, VerificationLatency — emitted before and after the Redis layer, so the improvement is a measurement rather than an estimate.
  • A purpose-built benchmark script exercised both cold and warm request paths. Benchmarking only the warm path would have produced a much prettier and much less true number.
  • Multi-AZ VPC, ALB, ECS Fargate and port-scoped security groups, provisioned and destroyed through 10 Terraform modules — so every measurement started from an identical stack.

what I would change

The cache key is per-ticket. For a draw with a small winning set, a negative-result filter in front of Redis would cut the Postgres fallback further — most verifications are losses, and those are exactly the reads currently doing the least useful work.

I would also put the WINNER exclusion behind a feature flag rather than a code path. It is the single rule most likely to need changing under operational pressure, and right now changing it means a deploy.
